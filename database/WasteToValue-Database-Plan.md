# Waste-to-Value Database Plan

## 1. Source of truth

Use one Neon PostgreSQL database and one ASP.NET Core `AppDbContext`. Entity Framework Core migrations are the production source of truth. The accompanying SQL file is the agreed initial-schema reference and can be used by the database integrator to verify the EF migration. Do not both run this SQL manually and then run an equivalent EF initial migration against the same database.

Only one nominated database integrator creates, reviews, applies, or repairs migrations. Members create entities and `IEntityTypeConfiguration<T>` mappings in their owned module, then provide a schema-change note.

## 2. Ownership

| Owner | Tables |
|---|---|
| Shared/integrator | `app_users`, `roles`, `user_roles`, `categories`, `agent_workflows`, `agent_steps`, `agent_tool_calls`, `approvals`, `audit_events` |
| Member 1 | `items`, `item_photos`, `item_answers`, `assessments`, `assessment_clarifications` |
| Member 2 | `recovery_cases`, `value_references`, `recovery_options`, `recovery_proposals`, `proposal_decisions` |
| Member 3 | `partners`, `partner_memberships`, `acceptance_rules`, `recipient_needs`, `matches`, `partner_responses` |
| Member 4 | `collection_slots`, `pickup_plans`, `pickup_requests`, `pickup_events`, `handover_proofs` |

No member creates a second users, items, partners, matches, proposals, or pickup table in their module.

## 3. Relationship flow

`app_users -> items -> assessments -> recovery_cases -> recovery_options -> matches -> pickup_plans -> recovery_proposals -> pickup_requests -> pickup_events`

The proposal is the approval boundary. It identifies an exact recovery option, match, pickup plan, and revision. A decision is valid only for that revision.

## 4. Important constraints

- UUID primary keys are generated by PostgreSQL.
- Money uses `numeric(12,2)` and a three-letter currency code.
- Timestamps use `timestamptz` in UTC.
- Mutable rows have integer `version` values for optimistic concurrency.
- Only one non-terminal recovery case may exist for an item.
- Only one current assessment may exist for an item revision.
- Partner capacity and need quantities cannot become negative.
- One proposal revision can receive only one decision per decision type/actor.
- One proposal can create only one pickup request.
- Agent JSON uses `jsonb`; hidden chain-of-thought is never stored.
- Completed business history uses restrictive foreign keys or soft/status transitions rather than cascade deletion.
- Exact owner addresses and handover proof are access-controlled and not copied into agent summaries.

## 5. Authentication note

The SQL uses a compact `app_users` model with UUID identifiers. Before implementation, the team must make one decision:

1. Customize ASP.NET Core Identity to use `Guid` keys and map its identity tables, or
2. Keep default Identity tables and replace `app_users` references with the chosen Identity user key type.

Do not create both competing user models. The database integrator must settle this before the initial EF migration. Password hashing is performed by ASP.NET Identity; never store plain-text passwords.

## 6. Migration workflow

1. Freeze entity names, user-key strategy, statuses, money precision, and shared IDs.
2. Merge entity/configuration changes one component at a time into an integration branch created from current `main`.
3. The integrator generates one ordered migration, reviews its `Up`, `Down`, and model snapshot, and creates a SQL script.
4. Test from an empty local PostgreSQL database.
5. Test upgrade from the last committed migration.
6. Merge migration and corresponding model changes together.
7. CI runs backend integration tests.
8. Apply to a Neon development branch/database first, then shared Neon.
9. Record migration ID, operator, date, target, and result.

Never rename migration timestamps, manually combine model snapshots, delete a migration already applied to shared Neon, or create tables through the Neon console. Repair deployed mistakes using a new corrective migration.

## 7. Member change request format

Every database-related pull request must include:

- Owned component and tables affected.
- Columns added/changed with nullability and defaults.
- Foreign keys and delete behavior.
- Unique constraints and indexes.
- Data backfill needed.
- Compatibility impact on existing API versions.
- Tests for constraints and transactions.
- Confirmation that the member did not generate or apply a migration.

## 8. Neon environments

- Each member uses a local PostgreSQL database or a separate Neon development branch.
- Shared Neon credentials live in user secrets or deployment environment variables.
- Only the integrator has permission to apply shared schema migrations.
- Applications may use a pooled runtime connection; schema migrations should use the direct connection supplied for administrative operations.
- Never commit a real connection string.

## 9. Initial deployment decision

Prefer generating the initial database from EF Core after all entity configurations match the agreed schema. Treat `WasteToValue-Initial-Schema.sql` as a reviewable specification. If the team deliberately chooses SQL-first initialization instead, execute it once on an empty database, then baseline EF carefully so it does not attempt to recreate existing tables.
